# Port paper-docx to Rust

Build a standalone Rust library and CLI that preserve paper-docx's document-editing behavior and refusal guarantees. An example first release opens a contract, finds an exact phrase split across multiple Word runs, replaces it, and saves a new file while preserving unrelated package parts. If the phrase is ambiguous or crosses an unsupported boundary, the document and existing output remain unchanged.

The confirmed delivery target is **a standalone Rust library plus CLI**. Full Python object-model compatibility and a WordCraft adapter are separate delivery tracks. The implementation remains Python-free at runtime; the pinned Python project is a development oracle. This document is a proposal; no Rust implementation has started.

### Evidence and baseline

Research snapshot: upstream **paper-docx 0.2.1, commit `3c0f9a5`**, inspected on 2026-10-19. Local Python 3.13 execution produced **3,003 passed, 7 skipped, 42 failed** in pytest; all 42 failures reported a LibreOffice launcher pointing to a missing application. Behave passed **67 features / 650 scenarios / 1,856 steps**. Independent-loader validation therefore remains unverified locally. These are baseline observations, not Rust test results or a coverage percentage.

The load-bearing upstream files are `src/docx/_zipguard.py`, `_paperpkg.py`, `_transaction.py`, `_ownership.py`, `story.py`, `_textatoms.py`, `search.py`, `revision.py`, `_compare.py`, and `composition.py`. The acceptance contract is in `tests/paper/harness/contract.py`; approved fork signatures are pinned in `tests/paper/test_api_surface.py`. All upstream links below refer to the inspected commit.

### Scope and compatibility

Port the **behavior and supported document structures**, exposing idiomatic Rust types and `Result` errors. Python import compatibility does not translate into a Rust API requirement. Preserve the seven named refusal categories plus malformed-package diagnosis; map programmer errors separately from safe refusals. Publish a capability matrix so a partial release makes its supported operations explicit.

Full behavioral scope includes ordinary document creation and inherited public authoring operations, inspection across stories, search and normalization, safe replacement, tracked changes and resolution, blocks and tables, styles and numbering, comments and threads, controls, bookmarks and fields, links and notes, picture replacement, formatting inspection, package diff/save, compare, and composition. The first usable release is the narrower M3 slice below; later milestones complete this scope.

Layout, pagination, PDF rendering, field-result calculation, legacy `.doc` support, encryption, macro authoring, network services, and a full `python-docx`-compatible Python facade are outside this port. Unknown content that can remain opaque is retained; operations whose safe effects cannot be proved return a typed refusal. Unsupported operations must never report success as a no-op.

### Architecture: retain the package, edit through typed views

Use an owned OPC package with original archive bytes, original bytes for each part, namespace-aware XML arenas, and typed views into those arenas. A partial OOXML data model must not be the serialization authority. Keep the library synchronous and independent of a GUI or async runtime. Separate filesystem save from byte-oriented core operations so a WASM adapter remains possible without promising WASM delivery now.

### Decisions to make durable in the core

**1. XML fidelity and namespaces.** Preserve ordered children, mixed text, whitespace, comments, processing instructions, unknown elements and attributes, and namespace declarations. Compare names by namespace URI plus local name, while retaining lexical prefixes and scope for serialization. Prefixes inside attribute values and `mc:Choice/@Requires` carry meaning: do not rewrite them blindly. Preserve opaque subtrees with their namespace context or refuse a relocation. Keep DOCTYPE/external entity processing disabled and validate malformed namespace use. Handle `mc:AlternateContent` through the same supported-choice policy used by story traversal. Avoid Serde-only OOXML structs as the storage model.

Use `quick-xml`'s namespace-aware event API behind this layer. Its writer is a serialization primitive, not a preservation guarantee. Include UTF-8 and UTF-16 decoding tests before committing to the parser configuration; retain original bytes of unchanged parts and emit a correct UTF-8 declaration when serializing a modified part. The M1 spike must prove namespace and opaque-node preservation before feature work proceeds.

**2. ZIP and save semantics.** Keep `_zipguard.py`'s validation independent of the chosen ZIP crate: duplicate and case-ambiguous member names, illegal OPC paths, file/directory prefix collisions, header inconsistencies, compression restrictions, truncated streams, actual inflated lengths, CRC and end-of-stream checks. Do not extract archives to disk or fetch external relationship targets. `zip` is the initial candidate; audit its exact version against hostile fixtures, including what its raw-copy APIs do not validate.

No-op patch save returns the original archive bytes. A changed save retains original uncompressed bytes for semantically unchanged parts; it does not promise the same ZIP container bytes or original byte ranges inside a changed XML part. Preserve the upstream special equality rules for relationships and content types. Produce deterministic changed output for fixed inputs within a pinned build; compressed bytes need not match Python's compressor. Save through a same-directory temporary file, flush, validate, and atomically replace. Specify and test Unix/Windows replacement, permissions and symlink behavior. On platforms where preserving a destination symlink cannot be implemented safely, return an explicit unsupported-save error before writing.

Runtime budgets are explicit `Limits` policy, with a distinguishable `ResourceLimit` outcome and a trusted/local profile. Bound compressed input and metadata, entry count, actual decompressed bytes per part and package, XML depth/nodes/attributes/namespace bindings, decoded text and normalization expansion, diff work, staged transaction memory, composition growth and serialized output. Check budgets before allocation or expensive work and during streaming, not just against declared sizes. Budget failure discards staging and preserves state and existing output. Upstream removed some size ceilings after Word measurements; Rust defaults must therefore be documented as a policy difference, never as evidence a valid document is malformed. Freeze exact defaults and compare-work budgets in M0.

**3. Handles, views and Unicode.** A document owns its XML; callers hold opaque span/block handles containing document identity, stable node identity, captured view and local freshness evidence. Editing takes `&mut Document`, preventing concurrent mutation through the safe API. Harmless insertions before a target must not invalidate it. Detach/replacement, ancestor moves into a different semantic owner, field/control/revision changes, or text changes must invalidate the affected handle. A global document revision counter alone is too coarse. Targets captured under `original` and `all` remain inspection-only; callers explicitly reacquire `current` targets for edits. Handle identities are session-local and never durable public anchors. Use non-reused node IDs plus structural generations: a detached node cannot be reinserted to revive an old handle. Cloned staging retains IDs only for the same logical nodes. Cloning an existing span aliases its consumption token; an independently acquired span has its own token and must pass freshness checks after any edit. Replacing the whole document creates a new document identity. Add properties for deletion/reinsertion, alias consumption, commit and rollback so handles never regain authority over replacement content.

Use Unicode scalar positions for externally reported text offsets, matching Python string indexing. Internally map scalar boundaries to UTF-8 byte ranges. Normalization must implement full case folding, punctuation translation, whitespace collapse and removal rules with a map back to source characters; `to_lowercase()` is insufficient for expansions such as `Straße → strasse`. Pin Unicode tables, Python whitespace predicates and any regex-dependent matching rules to the selected oracle; Rust character helpers are not assumed equivalent. Test expansions, uncommon whitespace, combining marks, Mongolian text and emoji. Unknown visible run content becomes a search barrier rather than disappearing.

**4. Atomic edits.** Validate first, stage changed XML parts and relationship/ID/cache changes in a copy-on-write overlay, then validate and commit the complete operation. Cloned arenas retain logical IDs for unchanged nodes. Keep target consumption and freshness updates in the same commit. No-op, refusal and failed commit leave supplied handles reusable; a successful text-changing replacement consumes the selected span, including aliases of the handle. Replacing a span with identical text is an explicit `Unchanged` report, performs no mutation, creates no revisions and leaves handles reusable; verify the tracked and preserve-revision variants against the oracle before freezing them. Failure injection must cover errors after each mutation phase. No public mutable XML escape hatch in the first release.

**5. Error and output contracts.** Separate `Refusal` (document unchanged), invalid caller arguments, resource policy, malformed input and I/O failure. Use stable machine-readable codes with human context; do not freeze exact Python exception prose. A successful in-memory edit and subsequent failed save are separate operations: the failed save preserves the destination file but does not undo a prior successful edit. A CLI operation publishes success only after its output is committed. Diagnostic JSON carries `schema_version: 1`; mutating CLI commands select and edit within one process rather than replaying serialized live handles.

**M3 edit boundary.** Ship untracked replacement only inside plain base-text runs sharing one concrete owner. Reject any changed interval inside pending revisions or fields, entering/leaving a hyperlink or content control, crossing positional markers or opaque atoms, or involving a protected/locked/data-bound target. Preserve unchanged affixes and starting-run direct formatting according to the upstream localization rule. Bookmarks surrounding an edit require a proved marker-preserving path; otherwise refuse. Declare these initial capability limits in the ledger and narrow refusals later as M4/M5 add supported structures. Every support/refusal cell needs a shared case proving the reopened result or unchanged state before M3 can ship.

Use the default document package as an MIT-licensed upstream reference with attribution or generate an independently tested minimal package; retain all inherited copyright notices in either case where source/assets are adapted. Inspect fixture provenance before redistribution. The corpus currently contains 31 generated, 9 LibreOffice-exported and 1 Google-exported DOCX files. Word-authored fixtures are not included in that corpus.

### Reuse the tests as a cross-language specification

Reuse the frozen fixture documents, hashes, ground truth, documented operations and meaningful acceptance scenarios. **Do not translate Python mock/proxy tests mechanically.** Convert each behavioral case into input fixture + operation + expected public outcome, error category, package-part budget and reopen assertions. Run the same cases through a pinned Python adapter and the Rust implementation. Classify every original test; any excluded implementation-specific test needs an explanation and a Rust invariant covering its risk where relevant. The existing 650 Behave scenarios are source scenarios to map, not automatic Rust coverage.

Port the safety suites first: kernel/manifest, ZIP preflight, package integrity, namespace collisions, text and structural atomicity, ownership/freshness, protection, and late failure rollback. Use `test_story.py`, `test_search_replace.py` and the audit suites to expand the first usable slice. Add compare and composition oracles when their dependencies are proven. Preserve bugs only when they are part of an intentional contract; log deliberate corrections such as QName-value comparison as compatibility deviations with explicit regression cases.

Every shipped mutator must prove: intended effect after save/reopen; exact expected changed/added/removed parts; no unexpected loss of unknown content; typed refusal with unchanged in-memory state, handles and supplied files; and independent-loader opening for representative outputs. Compare additionally proves accept/reject algebra using semantic package evidence, not text alone. Pin dates/IDs for deterministic cases. Treat the Python oracle as one reference alongside the public OOXML specification and external loader results.

### Verification and release acceptance

Proposed commands below are future deliverables. Native CI runs formatting, Clippy, unit/integration and shared case suites on Linux, macOS and Windows. Dedicated CI installs LibreOffice and requires actual successful PDF conversion; a broken launcher must fail environment setup clearly. Use property tests and fuzz targets for ZIP metadata inconsistencies, namespaces, XML limits, Unicode source maps, random edit sequences and malformed relationships. Assert no panic and no partial commit. Test resource budgets separately from invalid-document refusals. Benchmark open, outline, replace/save, compare and composition with realistic and large fixtures; record latency and peak memory against Python. Set numerical performance goals after measurements rather than assuming a Rust rewrite is faster.

For each end-to-end acceptance case: start from a copied frozen fixture, run a real CLI command, reopen output in Rust and Python, verify the part budget, and open it in LibreOffice. Repeat with an ambiguous target and a pre-existing sentinel output file: refusal must preserve the file exactly. Test same-path save and a simulated write failure. Full parity release requires a completed public capability ledger and no unexplained behavioral discrepancies. M3 may ship earlier under its explicitly smaller capability set.

### WordCraft and Python integration boundaries

The local `wordcraft/crates/docx/src/lib.rs` describes a lenient reader that skips unknown markup. Its `xml.rs` maps unknown namespace URIs to a `?:` prefix. These are useful choices for the current importer but cannot serve as preservation authority for this port. A future adapter should keep the original OPC/XML package alongside WordCraft's editable model and apply only proved edits through the new core. Reuse concepts and vetted low-level helpers after tests establish equivalence; do not silently route bounded edits through a full model export. Read WordCraft's own clean-room, asset and shared repository rules before any integration or fixture copying; no files there are changed by this proposal.

If Python users must migrate, first expose the new narrow operation API through PyO3/maturin. Full `docx.Document` proxy compatibility, object identity, lxml escape hatches and package-install collision handling require a separately scoped facade and test matrix. Keep Python dependencies out of the Rust core.
